## 2026-08-12 — filtergraph path escaping: promoted out of a shell module, rule derived empirically
- Symptom: `media_stabilize` failed on every Windows workspace. `pipelines/stabilize.py` interpolated the `.trf` path raw into `vidstabdetect`'s `result=` and `vidstabtransform`'s `input=`; inside a filtergraph `:` separates options and `\` escapes, so `C:\Users\...` ended the option value at the drive letter. Linux CI stayed green throughout. Separately, 16 unit tests failed locally on Windows (14 hardcoded POSIX path literals, 2 asserting the buggy unescaped output), so a local `pytest` run could not be trusted to surface real regressions.
- Fix: Promoted the escaper from a private `_escape_ff` in `server/bundles/subtitle_track.py` (a *shell* module the pipeline layer cannot import from) to `pipelines/_common.escape_filter_path`; wired stabilize's two call sites and the `subtitles_burn_in` `ass=` filter to it. Replaced `Path("/dev/null")` with `Path(os.devnull)` in stabilize pass 1 (`\dev\null` on Windows). Fixed the 14 portability assertions to compare `Path`-to-`Path` or against `str(Path(...))`.
- Surfaces (the expensive part): the first version of the promoted escaper was **wrong**, and so was the `_escape_ff` it came from — both used the plausible single-level rule (`\`->`\`, `:`->`\:`), which real ffmpeg rejects with `Error parsing filterchain`. That means `subtitles_burn_in` had been broken on Windows too: the duplication hid one shared defect behind the appearance of one correct implementation and one missing it. The unit tests written against the plausible rule passed and proved nothing, because implementation and tests encoded the same wrong model. Only feeding candidates to a real ffmpeg and checking whether `vidstabdetect` actually wrote its `.trf` settled it. A filtergraph is unescaped **twice** before a filter sees its argument, so: separators must become **forward slashes** (a native `\` is consumed by the second pass — `C:\Users` arrives as `C:Users`, and doubling does not help since each pass eats one), `:` needs **two** backslashes, `'` needs **three** (handled a pass earlier; two and four both fail), spaces need none. Verified 9/9 real-ffmpeg invocations across both stabilize passes and the `ass=` filter, each with a plain path, a path with a space, and a path with an apostrophe.
- Watch: any future change to `escape_filter_path` — re-run the real-ffmpeg probe rather than trusting the unit tests, which now encode the answer but cannot re-derive it. The escaping values in `tests/unit/test_common_filter_escape.py` and the vault note are empirical, not derived from documentation; treat them as measurements. Also: `_common.py` is at ~249 LOC against its documented ~250 LOC split trigger, so the next helper landing there should trip the package split.

## 2026-09-11 — a render against deleted footage reported success, because melt exits 0
- Symptom: `execute_render` treated melt's exit code as the whole truth (`if result.returncode == 0: succeeded`). melt does not fail when a producer's file is gone — it logs a warning, renders that clip as blank frames, and exits **0**. So deleting the media behind a timeline and rendering it returned `JobStatus.succeeded` with an output file that silently dropped those shots, and `render_preview` wrapped that in `status: "success"`. Nothing anywhere in the render path checked that referenced media exists. `tests/integration/test_workflow_failures.py::TestMediaMovedAfterIngest::test_render_after_media_deleted_does_not_report_success` is the test for exactly this and it **passed on the author's machine for the wrong reason**: that melt *hung* on missing media, and the test's 60 s timeout was counted as a failure (see `pass3-workflows-report.md:20`). CI's melt 7.22 exits 0 instead, so the first time `full` ran to completion the test failed — the only failure in the suite. The probe had never reached its subject.
- Fix: a precondition, `adapters/render/media_check.missing_media(project)`, read by `execute_render` (before it spawns anything) and by `pipelines/render_final.render_final`. It parses the XML **about to be rendered** and returns every file-backed producer resource that is not on disk; the render is refused and the message names each missing file. Why a precondition and not parsing melt's warnings: melt's wording is not API, varies by version and module, cannot separate a fatal missing source from a benign optional-service warning, and only discovers the problem after paying for the render. Reading the producer list is deterministic, costs milliseconds, and can name the files — which is the thing a user needs.
  Scope was the hard part, because a project legitimately contains producers with no file on disk. So the classifier is an **allowlist of file-backed `mlt_service` values** (`avformat`, `avformat-novalidate`, `qimage`, `pixbuf`, `timewarp`, `xml`), not a deny-list of synthetic ones. Every Kdenlive timeline carries `producer_black` (`mlt_service=color`, `resource=black`, written unconditionally at `serializer.py:485`), and `tests/integration/test_alpha_render.py` renders a `color` producer whose resource is `#00000000` through this same executor. Titles (`kdenlivetitle`, empty resource), `qtext`/`dynamictext`, generators and `frei0r.*` are all outside the allowlist, as is any service the check does not recognise. The cost is a narrower guarantee — a file-backed producer carrying no `mlt_service` is not checked — and the benefit is that this check can never refuse a render that would have worked. Remote URLs and image sequences (`%0Nd`, `.all.`, `glob:`) are skipped for the same reason: `Path.exists()` cannot settle them. `timewarp` stores `<speed>:<inner>`, so the speed is stripped first — and the inner may itself be synthetic (`patcher_intents` builds `2:color:black`) or a Windows path whose drive-letter colon must survive (`4.000000:C:/Videos/shot.mp4`).
  Placement matters and is not mode-aware on purpose. `run_render` rewrites the project for every mode except `"proxy"`, swapping producers back to their originals (`proxy_wiring.originals_render_copy`), and hands `execute_render` that copy. Checking inside `execute_render` therefore checks exactly the resources melt will open — the proxy paths in proxy mode, the originals otherwise — with no mode logic and no risk of failing a proxy render whose originals are archived, or a standard render whose proxy was deleted (which `test_render_swaps_to_originals_when_proxy_missing` requires to succeed). The check is skipped when the caller passes `_command_override`, the internal test hook that replaces the render command outright: the project is then not what runs.
  `RenderJob` gained `error_message` / `error_type` so a failure can say why. `render_preview` now returns a structured **error** when a render did not succeed, instead of `_ok({... "status": "failed"})` — the old shape reads as a completed render to anything that only checks the envelope.
- Surfaces: the test could not fail on the machine that wrote it, because a *hang* and a *refusal* both look like "not succeeded" to `assert result.status != succeeded`, and only one of them was the behaviour under test. Two controls now keep the fix honest, both in `tests/unit/test_render_media_check.py` so they run without melt: a render whose media is all present still succeeds, and a timeline of only colour/title producers still renders — without those, a check that refused everything would look like a fix. Mutation-checked on CI: reverting the executor's precondition turns the integration test red again on that exact case (run ids in the PR).
- Watch: (all three items below were closed by the next entry, "the missing-media rule existed twice and the two copies disagreed"; the non-producer file references and the round-trip re-basing were not.) the same hole is still open on **two** other melt paths that were found and deliberately not closed here. `pipelines/review_loop._render_kdenlive_frame` (review_loop.py:400) renders a still from a project with `check=False` and only asks whether a PNG appeared — a missing-media project yields a blank thumbnail and no error. `pipelines/motion_track.run_melt_tracker` runs melt over a single media file and never stats it. `bundles/subtitle_track` renders a whole project to burn subtitles in and **is** fixed here, since it is the same false-success shape. Also unchecked by `missing_media`: file references that are not producer resources — luma mattes (`pipelines/masked_wipes`, `pipelines/compositing`), the `shape` alpha mask, and the `av.filename` subtitle sidecar. And `adapters/kdenlive/validator.validate_project` still does the naive version of this check (flags `black` as "Media file not found", never strips a `timewarp` speed, and resolves relative paths against the workspace root rather than the `<mlt root>` attribute); it was left alone to keep this change to the render path, but it and `missing_media` now disagree about the same projects. Separately, `parse_project` never reads the `<mlt root>` attribute and `serialize_project` always rewrites it to the project file's own directory, so any round-trip of an imported project re-bases its relative resources — `missing_media` reads `root` from the file on disk and will correctly start reporting those.
- Commit: this entry's commit on `fix/ci-green-ffmpeg-profiles`.

## 2026-09-11 — the missing-media rule existed twice and the two copies disagreed
- Symptom: the previous entry's fix closed the render hole and, in doing so, created the defect shape this codebase keeps producing — one rule in two places. `adapters/kdenlive/validator.validate_project` still carried a naive version of the same question ("which producers name a file that must be on disk?") and answered it differently on real projects. Measured, one case at a time, by putting each case through **both** call sites:

  | case | old validator | `missing_media` | correct |
  | --- | --- | --- | --- |
  | `avformat` → absent file | refuse | refuse | refuse |
  | `avformat` → present file | accept | accept | accept |
  | `color` / `black` (every Kdenlive timeline carries it) | **refuse** | accept | accept |
  | `color` / `#00000000` (`test_alpha_render` renders it) | **refuse** | accept | accept |
  | `kdenlivetitle`, no resource | **warn** | accept | accept |
  | `timewarp` → `2.0:<present file>` | **refuse** | accept | accept |
  | `timewarp` → `2.0:<absent file>` | refuse, naming `2.0:/path` | refuse, naming `/path` | name the path |
  | `timewarp` → `4.000000:C:/Videos/gone.mp4` | **refuse**, naming the speed too | refuse, drive letter intact | keep the drive letter |
  | `timewarp` → `2:color:black` (`patcher_intents` builds these) | **refuse** | accept | accept |
  | `avformat` → `https://…/clip.mp4` | **refuse** | accept | accept |
  | `qimage` → `/frames/f_%05d.png` | **refuse** | accept | accept |
  | unknown future service → `/nope.bin` | **refuse** | accept | accept |
  | relative resource present under `<mlt root>` | **refuse** | accept | accept |
  | relative resource absent under `<mlt root>` | refuse, naming the workspace-relative path | refuse, naming the melt-resolved path | resolve like melt |

  Eleven of fourteen disagreed, and in every one of those eleven the *validator* was the wrong one. A user validating a normal project with a title card, a speed ramp and the colour background Kdenlive puts in every timeline got a report full of "Media file not found" for files that were never supposed to exist.
- Fix: one implementation, in `adapters/render/media_check`. `resource_to_path(service, resource)` is the classifier (unchanged behaviour, now public); `resolve_missing(triples, base)` is the shared core over `(producer_id, mlt_service, resource)` plus the directory relative resources resolve against; `missing_media(project_path)` is the XML front door and keeps its signature. The validator builds triples from `project.producers` and calls the core — it no longer contains the rule, only the report-shaping. Two seams had to be handled honestly rather than papered over:
  - *An in-memory producer may carry no `mlt_service`.* The serializer defaults those to `avformat` when the resource looks like a path, so a bare allowlist applied to the model would have silently stopped checking every producer this repo builds. `serializer._looks_like_media` became `looks_like_media_resource` (public) and the validator applies the serializer's own default before asking. The validator therefore answers for the file that *will be written*, which is the file melt will open.
  - *Where does a relative resource resolve?* melt uses the `<mlt root>` attribute; the validator was using the workspace root. `parse_project` had been dropping `root` entirely, so there was nothing to use. It now keeps it (`KdenliveProject.root`), and the validator resolves against it, falling back to `workspace_root` for a project built in memory. `ValidationItem` gained `path` — the resolved path as data, so a caller (or a test comparing the two call sites) does not parse English out of `message`.
  - The blanket "Producer 'x' has no resource path" warning fired on every title card in every project. It now fires only when the producer's service says it is file-backed, which is the case that is actually broken.
- Fix, part two — the two other melt paths the previous entry listed as still open. They did **not** want the same answer, and saying so was half the work:

A degraded mode was considered and rejected — a thumbnail is a publish artifact, the caller cannot distinguish a deliberately dark frame from a failed one, and a blank thumbnail is exactly what gets uploaded. (It is also not free of false refusals: the missing clip may not be the one under the requested timestamp. Refusing with the filenames is still better than a black PNG labelled success, and the user can point the tool at a media file instead.)
  - `pipelines/motion_track.run_melt_tracker` is handed **one media file**, not a timeline. There are no producers to classify and no XML to parse, so reusing `missing_media` there would have meant parsing a document that does not exist. It stats its source and names it. What the three share is the reason — melt does not check its inputs, so the caller must — not the code. The old behaviour was worse than silence: a moved file produced no tracker results and was reported as "the opencv module may be missing, or the content lacks trackable texture", sending the user to install an MLT module over a file they only had to relink. `run_opencv_tracker` had always named it correctly.
- Surfaces: the duplication was one day old and still cost eleven wrong answers, because the second copy was written first and looked finished. The thing that made it tractable was refusing to test the two sides separately: `tests/unit/test_media_check_reconciled.py` states each case **once** and runs it through both call sites, so "they agree" and "they are right" are separate assertions and neither alone can pass. That matters — under the mutation that makes the core report nothing, every `test_the_two_agree` still passed (both sides agree on "nothing is missing"); only the per-side verdicts caught it.

## 2026-09-11 — the render opens files that are not producer resources, and none of them were guarded
- Symptom: the precondition from the previous entry only ever looked at `<producer>`/`<chain>` `resource` values, and the previous entry's own Watch note said so. A render opens more than that. A `luma` wipe reads a grayscale matte, `shape` (Shape Alpha) reads a mask image or video, `avfilter.subtitles` reads an `.ass`/`.srt` sidecar, `avfilter.lut3d` reads a `.cube`. melt treats a missing one exactly as it treats missing footage — logs, renders something wrong, exits **0** — so the silent success the precondition exists to close was still reachable through four other doors. - How the list was found, rather than guessed: two mechanical surveys, cross-read.
