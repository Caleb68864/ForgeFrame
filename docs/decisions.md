## 2026-08-12 — filtergraph path escaping: promoted out of a shell module, rule derived empirically
- Symptom: `media_stabilize` failed on every Windows workspace. `pipelines/stabilize.py` interpolated the `.trf` path raw into `vidstabdetect`'s `result=` and `vidstabtransform`'s `input=`; inside a filtergraph `:` separates options and `\` escapes, so `C:\Users\...` ended the option value at the drive letter. Linux CI stayed green throughout. Separately, 16 unit tests failed locally on Windows (14 hardcoded POSIX path literals, 2 asserting the buggy unescaped output), so a local `pytest` run could not be trusted to surface real regressions.
- Fix: Promoted the escaper from a private `_escape_ff` in `server/bundles/subtitle_track.py` (a *shell* module the pipeline layer cannot import from) to `pipelines/_common.escape_filter_path`; wired stabilize's two call sites and the `subtitles_burn_in` `ass=` filter to it. Replaced `Path("/dev/null")` with `Path(os.devnull)` in stabilize pass 1 (`\dev\null` on Windows). Fixed the 14 portability assertions to compare `Path`-to-`Path` or against `str(Path(...))`.
- Surfaces (the expensive part): the first version of the promoted escaper was **wrong**, and so was the `_escape_ff` it came from — both used the plausible single-level rule (`\`->`\`, `:`->`\:`), which real ffmpeg rejects with `Error parsing filterchain`. That means `subtitles_burn_in` had been broken on Windows too: the duplication hid one shared defect behind the appearance of one correct implementation and one missing it. The unit tests written against the plausible rule passed and proved nothing, because implementation and tests encoded the same wrong model. Only feeding candidates to a real ffmpeg and checking whether `vidstabdetect` actually wrote its `.trf` settled it. A filtergraph is unescaped **twice** before a filter sees its argument, so: separators must become **forward slashes** (a native `\` is consumed by the second pass — `C:\Users` arrives as `C:Users`, and doubling does not help since each pass eats one), `:` needs **two** backslashes, `'` needs **three** (handled a pass earlier; two and four both fail), spaces need none. Verified 9/9 real-ffmpeg invocations across both stabilize passes and the `ass=` filter, each with a plain path, a path with a space, and a path with an apostrophe.
- Watch: any future change to `escape_filter_path` — re-run the real-ffmpeg probe rather than trusting the unit tests, which now encode the answer but cannot re-derive it. The escaping values in `tests/unit/test_common_filter_escape.py` and the vault note are empirical, not derived from documentation; treat them as measurements. Also: `_common.py` is at ~249 LOC against its documented ~250 LOC split trigger, so the next helper landing there should trip the package split.
- Commit: this entry's commit on `main`.

## 2026-08-12 — filtergraph audit: two more silent-failure sites, plus an external oracle
- Symptom: the escaping fix had only covered the two sites already known to be broken. These fail *worse* than stabilize did — both callers read the stats file back behind an `if stats_file.exists()` guard, so on Windows `clips_qc_scan` returns "no quality issues" and `detect_scenes` returns "no scenes" instead of erroring. A tool that confidently reports nothing wrong is more damaging than one that crashes. Confirmed against real ffmpeg before fixing (rc≠0, zero bytes written).
- Fix: Routed both through `escape_filter_path`; verified with real ffmpeg (rc 0, 25 KB of stats written; scene detection needs a source with an actual hard cut, so the probe concatenates two lavfi sources). ## 2026-08-28 — subprocess timeouts enforced by a scanner, not a sentence in CLAUDE.md
- Symptom: CLAUDE.md said "all ffmpeg subprocess calls must pass `timeout=`", scoped to `adapters/ffmpeg/*`. An AST sweep of the whole tree found 29 `subprocess.run` sites with no ceiling — capability probes (`ffmpeg -filters`), frame extracts, loudness/silence/scene scans, a full VFR transcode, the melt review render. Any wedged child (a Store-alias binary, an AV-scanner stall on a fresh output, a codec looping on a truncated container) hung the MCP server forever; the client RPC timed out with nothing diagnosable. `generate_proxy` did have a ceiling but left the truncated partial `.mp4` behind, and that partial then passed the "proxy already up-to-date" mtime check on the next call — a silent bad proxy.
- Fix: Three named tiers in `adapters/ffmpeg/runner.py` (`CAPABILITY_TIMEOUT_SECONDS` 30s, `ANALYSIS_TIMEOUT_SECONDS` 600s, `DEFAULT_TIMEOUT_SECONDS` 3600s) so every site picks from a vocabulary instead of inventing a number. Best-effort helpers that return `None`/`False`/`0` add `subprocess.TimeoutExpired` to their `except` tuple — it is a `SubprocessError`, not an `OSError`, so the existing `except (OSError, ValueError)` would have let it escape. `tests/unit/test_subprocess_timeouts.py` walks the source ASTs (module-attribute, aliased-module and bare-imported call shapes; a `**kwargs` splat is accepted as a forwarded ceiling) and fails on any blocking call without one. `tool_guard`/`from_exception` classify `TimeoutExpired`, `FFmpegTimeout` and `FFmpegNotFound` into an actionable error (`timed_out_after`, `binary`, install hint) at WARNING level — a timeout is a known condition, not a "please report it" bug. `generate_proxy` takes `timeout=` and unlinks the partial on timeout/failure.
- Surfaces: the rule had drifted the moment the first pipeline built its own argv instead of going through `run_ffmpeg`; a rule that lives only in prose is re-violated by the next drop-in bundle. The scanner is the durable form. The proxy smoke test had also drifted — it expected a raw `TimeoutExpired` from an adapter that had long since wrapped it in `FFmpegTimeout`, and it passed a `timeout=` kwarg the function did not accept, so it had been failing on every machine and nobody could tell it apart from the melt-absent noise.
- Watch: the tiers are ceilings against a *wedged* process, not budgets — a legitimately huge analysis pass on a multi-hour source could hit `ANALYSIS_TIMEOUT_SECONDS`; if that ever happens, raise the tier rather than sprinkling a bespoke number. `Popen` is deliberately out of the scanner's scope (its ceiling is on `communicate()`/`wait()`); nothing on the request path uses it today — extend the scanner if that changes.
- Commit: this entry's commit on `main`.

## 2026-08-28 — scratch frames never beside the source video; a flaky test was a real defect
- Symptom: `test_research_select_candidate_refuses_export_into_candidates_dir` failed once with `WinError 32` on `tests/fixtures/media_generated/greenscreen_reporter_720_frame_3_500.png` — a file that should not exist. `extract_frame` defaulted its output to `video_path.parent`, so every burst / `generate_candidates` / handshake / `research_video` run wrote scratch PNGs *next to the user's source video* (`media/raw/` is a protected tree), `shutil.move`d the survivors into `output_dir/candidates/`, and left every deduped/dropped candidate behind as an orphan. Two concurrent runs on the same file raced on identical filenames. The unit test carried a comment admitting "the adapter has no output-dir control" and the vault note listed it as a known caveat; the `.gitignore` had a pattern hiding the orphans.
- Fix: `output_dir` threaded adapter → `generate_candidates` → handshake/service → `research_extract_frame_burst` tool and `wvb frame`. The handshake extracts into a private `.frames-*` scratch dir *inside* `output_dir` (same filesystem, so the survivor move is a rename) and removes it in a `finally`. `research_video` uses a temp scratch dir; `export_package` repoints every retained candidate's `image_path` at its exported copy (selected → `screenshots/`, the rest → `candidates/NNN/` when `keep_candidates`), and anything not retained gets an empty `image_path` before the scratch dir is deleted — an honest value, never a dangling one, since `research_run` and the CLI `--json` dump serialise those paths. The tool/CLI default is a `<stem>_frames/` sibling folder, never the source's own folder. Regression suite `tests/integration/test_frames_never_beside_source.py` copies the fixture into an isolated `media/raw/` and asserts the directory holds nothing but the video afterwards.
- Surfaces: "flaky" was the wrong diagnosis — the flake was the only visible symptom of a safety-rule violation (never write into `media/raw/`) that had been documented as a caveat three times instead of fixed. Fixing it exposed three more bare `generate_candidates(...)`/`extract_frame_burst(...)` calls in smoke tests that had been polluting the fixtures dir on every run; the orphans were git-ignored, so `git status` never showed them.
- Watch: `extract_frame`'s beside-the-source default still exists for the explicit single-frame CLI/tool call. Any new pipeline that extracts more than one frame must pass `output_dir` — the regression suite catches the four known consumers, not a fifth. The `research_video` in-memory manifest now has empty `image_path` on non-retained candidates; a consumer that assumed every candidate has a file should check for the empty string.
- Commit: this entry's commit on `main`.

## 2026-08-28 — resource paths forward-slashed at the serializer; nine Windows-only test assertions
- Symptom: while fixing an `ai_mask` test's path-literal assertion, the next line down checked the `resource` written *into the `.kdenlive` file* and it held `C:\...\clip_matte.mp4`. Hard rule 6 (resource paths use forward slashes even on Windows; backslashes confuse Kdenlive's bin loader) was documented against the serializer but enforced nowhere — `escape_filter_path` normalises ffmpeg filtergraph paths, but producer `resource`, the `shape` mask `resource` and the `luma` wipe `resource` were all passed through verbatim from `str(Path)` at the tool boundary. Linux CI can never see this. Separately, nine test assertions compared paths against POSIX literals or `str(Path)` (`'media/processed' in p`, `.endswith("media/raw/clip.mp4")`, `== str(proxy)`), so they failed only on Windows and buried real Windows failures in noise — the same class the 2026-08-12 entry fixed 14 of.
- Fix: normalised at the serializer's single `resource` write site (`producer.resource.replace("\\", "/")`) plus the two filter/transition builders (`shape_alpha._shape_inner_props`, `masked_wipes.apply_masked_wipe`). `tests/unit/test_serializer_resource_slashes.py` feeds a literal backslash path so Linux CI exercises the normalisation too. The nine assertions now compare `Path(...).as_posix()` per the CLAUDE.md portability rule. Three melt-dependent review-loop tests gained `@requires_melt` (they failed outright on a machine without melt; CI installs melt so they still run there).
- Surfaces: a Windows-verified smoke output in the user's hands (memory: Kdenlive 25.08.3 opens them) does not prove rule 6 holds in general — those smokes were built from workspace-relative or already-posix inputs. The defect only appears when a tool receives an absolute Windows path, which is exactly what an MCP client on Windows sends. The test-side path literals are a recurring tax: every Windows-only failure costs a triage pass to separate "test is non-portable" from "product is broken", and this session found one of each on the same line pair.
- Watch: `kdenlive:proxy` and `kdenlive:originalurl` are also path-valued properties and are *not* normalised (they flow through the generic properties loop). No evidence yet that Kdenlive's loader chokes on them; if a Windows user reports a proxy that will not attach, that is the first place to look. New tests: assert `Path`-to-`Path` or `.as_posix()` — never a bare POSIX literal.
- Commit: this entry's commit on `main`.
